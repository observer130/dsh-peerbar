### 1.2 模块解析（影响代码怎么写）

从 profile 目录和插件目录都**解析不到** `@deepseek-ai/schemastery` / `@deepseek-ai/cordis`（`ERR_MODULE_NOT_FOUND`）——它们只在 `resources/app/dsh/node_modules` 下。`dshmarket` 虽然声明了这两个 peerDependency，但它的 `lib/index.js` 里**根本没有 import**，所以「声明了就能解析」是错觉。

**结论：v0.1 不 import Schemastery。** 不导出 `Config` schema，改在 `apply(ctx, config)` 里手写校验，校验失败用 `[peerbar]` 日志报出来。若日后确认宿主侧能解析，再换回 schema。

### 1.3 nv50 现场

| 探测 | 结果 |
| --- | --- |
| `GET https://192.168.3.50:3080/` | 证书自签，默认校验失败 |
| 加 `-k` | `401` + `dsh web authentication required; …` |
| `GET http://…:3080/` | 空响应 → 只有 HTTPS，没有 http 退路 |
| `GET /dsh-peerbar/api/health`（未注册） | `404`（非 401、非 SPA HTML） |

### 1.4 三条改变方案的结论

**A. 手动令牌 → API cookie → HTTP Remote 调用，全链路可用（详见 `docs/spike-S1.md`）。**
`GET /connect?token=…&interactions=none` 返回 `302` + `Set-Cookie: dsh-auth-<audience>`（30 天、HttpOnly、SameSite=Strict、Secure）。带该 cookie `POST /api/session/list` 返回 26 条会话。
→ 远端**不需要装 peerbar**，v1 的 provider 方案作废；也不需要 WS。

**B. `/api` 用 Connection 的 RPC 信封，不是 `{args}`。**
`{type:"client-request", rpcId, method, payload:{args:{…}}}`，`method` 必须等于路径尾部，`args` 键名用 descriptor 的 wire 名（`session/list` 是 `_request`）。

**C. 远端没有工作区读端点。**
`workspace/*` 全是写操作，`session/list` 也不返回 `workspaceId`，只有 `cwd`。
→ v0.1 的「工作区」按 `cwd` 分组合成，组名取 basename。这一条要写进 UI 文案与需求修订。

## 3. v0.1 定稿架构

### 3.1 只有 consumer，没有 provider

```
浏览器（本机 dsh 页面）
   │ 同源 fetch，只连本机
   ▼
本机 dsh 宿主（插件宿主半）
   ├─ guard.js        回环 + 同源栅栏
   ├─ peers.js        每 Host 一个探活/拉取状态机
   └─ remote.js       换 cookie、发 RPC 信封、解析结果
         │ HTTPS + cookie
         ▼
   nv50 / m50 的 dsh /api（不需要装任何插件）
```

- 远端只被读，不改任何东西；不加载远端 UI。
- 每个 Host 独立并发、独立退避，单台失败不影响 `/state`。

### 3.2 本机暴露的路由（全部过 guard）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/dsh-peerbar/api/health` | 免鉴权，`{ok, version}`，安装自检用 |
| GET | `/dsh-peerbar/api/state` | 全量快照（本机 + 各 Host 状态与数据） |
| POST | `/dsh-peerbar/api/hosts` | 新增 `{name, origin, token, tls}` |
| PATCH | `/dsh-peerbar/api/hosts/<id>` | 改名/改色/改令牌/改 tls |
| DELETE | `/dsh-peerbar/api/hosts/<id>` | 移除并清缓存 |
| POST | `/dsh-peerbar/api/hosts/<id>/probe` | 立即探活 + 重拉 |

带参数的路径注册一个 `kind:'prefix'` 的 `/dsh-peerbar/api/hosts`，在 handler 内解析尾段与 method；固定路径用 `kind:'exact'`。

### 3.3 远端调用（remote.js）

```js
// ① 换 cookie：只在新增 host 或收到 401 时执行
GET <origin>/connect?token=<token>&interactions=none
  → 302 + Set-Cookie（按 origin 存 jar，http/https 不通用）

// ② 调用：v0.1 所有读取都走这一个函数
POST <origin>/api/session/list
  {"type":"client-request","rpcId":"<uuid>","method":"session/list",
   "payload":{"args":{"_request":{}}}}
  → { type:"server-response", rpcId, result:{ ok:true, value:{ items:[…] } } }
```

错误映射：

| 远端表现 | 归类 |
| --- | --- |
| 连接拒绝 / DNS / 路由不可达 | `unreachable` |
| TLS 校验失败（`UNABLE_TO_VERIFY_LEAF_SIGNATURE` 等） | `tls-error` |
| `401` | `auth-required`（cookie 失效 → 提示重贴令牌） |
| `404` 或非 JSON | `not-dsh` |
| `result.ok === false` 且 `code` 以 `gateway/` 开头 | `incompatible`（协议对不上） |
| 超时 | `timeout` |

### 3.4 数据契约

```jsonc
// GET /dsh-peerbar/api/state
{
  "ok": true,
  "local": { "hostId": "local", "status": "online", "workspaces": [ /* 同下 */ ] },
  "hosts": [
    {
      "hostId": "h_9f2c1a7e", "name": "nv50", "origin": "https://192.168.3.50:3080",
      "color": "teal", "order": 1, "status": "online", "code": null,
      "latencyMs": 42, "hasToken": true, "hasCookie": true,
      "fetchedAt": 1761100000000, "stale": false,
      "workspaces": [
        {
          "id": "peerbar:h_9f2c1a7e:ws:/home/nwj/Projects/dsh-peerbar",
          "name": "dsh-peerbar",
          "cwd": "/home/nwj/Projects/dsh-peerbar",
          "sessions": [
            { "id": "peerbar:h_9f2c1a7e:sess:s_9", "rawId": "s_9",
              "title": "…", "lastActivityAt": 1761099000000,
              "running": false, "blank": false }
          ]
        }
      ]
    }
  ]
}
```

- **工作区是合成出来的**：按 `cwd` 分组，`id` 用 `cwd` 而不是远端 workspaceId（远端不给）。组名 = `basename(cwd)`，完整路径放 UI 的 title。
- 会话字段来自 `session/list`：`sessionId`、`cwd`、`updatedAt`、`running`、`blank`、`projections.values.title`。
- 令牌与 cookie **不出现在任何响应里**，只有 `hasToken` / `hasCookie`。
- 虚拟 ID：`peerbar:<hostId>:ws:<cwd>` / `peerbar:<hostId>:sess:<sessionId>`。

`~/.dsh/dsh-peerbar.json`（0600，宿主读写，前端不可见）：

  "hosts": [
    {
      "id": "h_9f2c1a7e", "name": "nv50", "origin": "https://192.168.3.50:3080",
      "order": 1, "enabled": true, "color": "teal",
      "tls": { "allowSelfSigned": true, "caFile": null },

### 3.7 客户端注册（按 slot-catalog 核实）

```js
const NS = 'dsh-peerbar'
function apply(ctx) {
  ctx.effect(() => ctx.locale.register(NS, { zh, en }), 'peerbar: dicts')
  const t = ctx.locale.bind(NS)
  ctx.slots.inject('sidebar.panellist', () => ctx.slots.register(
    { name: 'sidebar.panellist', id: 'peerbar', order: 120, label: () => t('panel.label') },
    PeerbarIcon,                       // props: { size, active }
  ))
  ctx.slots.inject('main', () => ctx.slots.register(
    { name: 'main', key: 'peerbar' }, PeerbarPage,
  ))
  ctx.slots.inject('settings.section', () => ctx.slots.register(
    { name: 'settings.section', id: 'peers', order: 900,
      locale: NS, label: () => t('section.peers') }, PeersSection,
  ))
}
```

- `panellist` 的 `id` 与 `main` 的 `key` 同名即可，侧栏按 id 自动分派，不需要点击回调。
- 组件通过注册项的 `locale: NS` 拿 `t` prop（`usage-stats` 同款写法）。
- 图标自绘 SVG，`currentColor`，不引第三方图标包。

## 7. 风险登记

| ID | 风险 | 触发信号 | 应对 |
| --- | --- | --- | --- |
| R1 | cookie 失效（30 天到期 / 远端凭据重置） | 请求 401 | 状态转 `auth-required`，设置页提示重贴令牌；换到即恢复 |
| R2 | 远端重启后 cookie 是否仍有效未实测 | 重启 nv50 后 401 | 若失效，退化为「每次重启重贴令牌」（用户已接受） |
| R3 | `session/list` 无分页/无 workspaceId | 会话多时一次返回过大 | v0.1 全量拉；超 500 条再试 `cursor` |
| R4 | 远端 `--trusted-host` / 反代导致 Host 不匹配 | 403 | 错误码文案提示「地址需与远端绑定一致」 |
| R5 | 探活把 404 当 not-dsh，但某些版本可能 fallback 成 200 HTML | 升级后误判 | 只看状态码 + `content-type`，不认 body 文案 |
| R6 | 回环栅栏挡住 LAN 浏览器 | 有人从别的机器打开本机 dsh | v0.1 不支持（与 P0-5 一致）；v0.2 加 `allowLanOrigins` |
| R7 | 令牌/cookie 明文落盘 | — | 0600 + 不回显 + README 告知；v0.2 考虑 keyring |
| R8 | 桌面版重启成本高 | 改宿主半要重启 | 宿主半逻辑抽纯函数走单测，路由层只装配 |
