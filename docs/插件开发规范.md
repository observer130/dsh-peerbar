## 1. 一句话模型

> dsh 插件 = 一个 Cordis 插件模块（导出 `name` + `apply(ctx)`），可选地带一个**浏览器半**；两侧都通过 `ctx` 注册能力，卸载时框架自动回收。

两半的能力面完全不同：

| | 宿主半（Node） | 客户端半（浏览器） |
| --- | --- | --- |
| 入口 | `package.json` 的 `main` | `package.json` 的 `exports["./client"]` |
| 声明 | `name` / `apply(ctx, config)` / `inject` | `exports.name` / `exports.apply` / `exports.inject`（在 `__ModuleLoader__` bundle 内） |
| 能力 | `ctx.webServer`、`ctx.settings`、`ctx.sessionController`、`ctx.workspaceRegistry`、`ctx.credentials`、`ctx.logger`… | `ctx.slots`、`ctx.locale`、`ctx.layout`、`ctx.workspaces`、`ctx.sessions`… |
| 发现方式 | Loader 读到 patch 行即挂载 | 宿主编译期扫描 `dsh.client` 声明，注入 `window.__DSH_BOOT__` 图 |
| 热更 | 改代码必须重启 dsh | 刷新页面即可（`hmr` 在场时会自动重载） |

**两半之间没有直连通道。** 客户端半只能：① 走同源 HTTP 打自己宿主半注册的路由；② 走 Typert Remote（`ctx.remote.*`，需构建期代码生成）；③ 读其他官方 Cordis service 的公开面。本项目选 ①。

## 2. 包清单（`package.json`）

### 2.1 组合包（bundle）——本项目采用

```json
{
  "name": "dsh-peerbar",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "exports": {
    ".": "./lib/index.js",
    "./client": "./lib/client.js"
  },
  "files": ["lib/", "cordis.patch.yml", "docs/"],
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "inject": ["@deepseek-ai/dsh-client-locale", "@deepseek-ai/dsh-client-ui-primitives"]
    }
  },
  "engines": { "dsh": ">=0.2.1-rc.1 <0.3.0" },
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.5",
    "@deepseek-ai/dsh-client-ui-slots": "^0.2.1-rc.1",
    "@deepseek-ai/dsh-client-ui-primitives": "^0.2.1-rc.1"
  }
}
```

**【已核实】** 各字段语义（`docs/user/develop/basic/publish.zh.md`、`docs/subsystems/client-modules.zh.md`、两份真实插件清单）：

- `dsh.bundle.patch`：一个 patch 条目数组的 YAML 文件；profile 列表里有你时应用这一层。可以是字符串或有序文件数组。
- `dsh.client.platform`：目前只有 `'web'`。
- `dsh.client.inject`：**包名**边（客户端模块依赖），不是 Cordis service 名。写进来的包，其 factory 先到达。
- `exports["./client"]`：必须指向**已构建/已手写的**浏览器 bundle；宿主不会 TS 编译你的源码。
- `engines.dsh`：安装与 profile 启动都会校验；**不满足直接拒绝启动**（缺失时退化为校验 `@deepseek-ai/dsh*` peer 范围）。**必须写。**
- `peerDependencies` + `devDependencies` 双声明：运行时用 profile 里的副本，devDependencies 只供类型检查。**禁止**把 `react` / `react-dom` / `@deepseek-ai/dsh-client-ui-primitives` 打进自己的 bundle —— 它们在浏览器模块表里是 baseline external，`require('react')` 由宿主提供。

### 2.2 patch 文件

```yaml
# cordis.patch.yml
- insert:
    - id: peerbar
      name: dsh-peerbar
      config:
        probeIntervalMs: 5000
```

**【已核实】** 行的 `name` 用**包名**（不是相对路径）；`id` 用于后续层覆盖（`- id: peerbar` 可整行替换 config，注意是替换整个 `config` 对象，不是深合并）。

### 2.3 另一种形态：`.dsh-plugin` 仓库插件

社区面板（`@dsh-external/plugin-console` + `$DSH_HOME/cordis.patch.yml`）支持 `dsh.plugin.json` + `manifestVersion: 1` 的目录形态，改文件立即生效、不重启。**不是内核机制**，属于可选分发形态；`DSH-better-sidebar` 同时提供两套。v0.1 不做。

## 3. 宿主半规范

### 3.1 入口与依赖声明

```js
export const name = 'dsh-peerbar'
export const inject = ['webServer', 'settings', 'workspaceRegistry']  // 静态声明
export function apply(ctx, config) { /* ... */ }
```

- **【已核实】必须静态 `export const inject`**，不要指望 `apply` 里手动等。`dsh-fleet` README 记录的「webServer 未就绪导致全新启动静默失效」，根因就是没声明 `inject`；Cordis 的规则是「依赖就绪后才调用 `apply`」。`ctx.inject(deps, cb)` 是另一种受支持写法，但静态声明是官方教程的默认姿势，也更容易审。
- `name` 是组合中的唯一 id，也被 patch 用来定位，取包名。
- `Config`：导出同名 `Schemastery` schema（`import Schema from '@deepseek-ai/schemastery'`），默认值写在 schema 里；非法配置在加载时**响亮失败**。原则：凡不同部署可能取不同值的都做成配置字段（dsh 官方明写的约定，`basic/config.zh.md`）。

### 3.2 路由注册

```js
ctx.effect(() => ctx.webServer.register({
  kind: 'exact',                       // 'exact' | 'prefix'
  path: '/dsh-peerbar/api/state',
  handler: (req, res) => { /* Node IncomingMessage / ServerResponse */ },
}), 'peerbar: state route')
```

**【已核实】**（`dsh-host-webserver/README.zh.md` §注册路由 + `usage-stats/lib/index.js:1512` 实拍）：

- handler 是**原生 Node** `(req, res)`，不是 Fetch `Request/Response`。
- 匹配顺序：先全表 exact → 再最长 prefix → 最后 fallback（SPA dist 占着）。重复路径注册**直接抛错**，所以路径一律带 `/dsh-peerbar/` 前缀。
  **【实测 2026-10-22 修正】** 在本机 desktop build 上，未注册路径返回的是 **404 纯文本**，不是 SPA 的 200 HTML（带不带 `Accept: text/html` 都一样）；`GET /` 仍被登录门拦成 401。所以「没装插件」可以靠 404 判定，探针不必解析 body。
- 用 `ctx.effect(...)` 包住以取得 disposer；handler 抛错 → 400 + warning，不会拖垮进程。
- `ctx.webServer.port` / `.protocol` / `.getOrigin()` 是只读组合期事实。
- `registerUpgrade({ path, handler })` 可拿原始 socket（仅 exact）；本项目 v0.1 不用。

### 3.3 鉴权：**插件自己的路由默认是裸的**

**【已核实】** 这是最容易被忽略的一条：

- dsh 的浏览器认证 + Host/Origin 信任（`sec-fetch-site: cross-site` 一律拒、403/401）**只由 `dsh-client-connection` 施加在唯一的 `/api` 路由上**。web-server 明确写着「不提供服务器级认证或来源策略」。
- 因此 `/dsh-peerbar/api/*` 的「同源 + 回环」校验必须**插件自己实现**，否则需求 §P0-5 的验收项（`Origin: http://evil` → 403）不会自动成立。

参考实现：`dsh-fleet` 与 `dsh-market` 都在自己的路由里手写同源/回环判断。本项目按需求 §8.6 的 `denied` code 自己写一个 `guard.js`（校验 `Host` 是否回环或等于绑定地址、`Origin` 是否同 authority、`sec-fetch-site` 非 cross-site）。

### 3.4 读本机数据用的服务

**【已核实】** 这些 ctx 键存在（包 README 的 「ctx 键」栏）：

| ctx 键 | 包 | 用途 |
| --- | --- | --- |
| `ctx.webServer` | dsh-host-webserver | 路由 |
| `ctx.settings` | dsh-settings | 设置读写 |
| `ctx.credentials` | dsh-credentials | 密钥/凭据记录（cookie 签名密钥也在这） |
| `ctx.workspaceRegistry` | dsh-workspace | 本机 workspace 记录 `list()` |
| `ctx.workspaceController` | dsh-api-workspace-controller | workspace 投影/变更 |
| `ctx.sessionController` | dsh-api-session-controller | session 列表、投影、历史 |
| `ctx.remoteAccess` | dsh-api-remote-access | 非 owner 访问判定 |
| `ctx.connection` | dsh-client-connection | Peer 认证、`admit()`、`fetch()` |
| `ctx.logger` | 内核 | 日志（前缀 `[peerbar]`） |

### 3.5 其它硬约定

- 一切注册走 `ctx.effect` 或直接 `ctx.xxx.register`（Cordis 会回收）；**不要**裸 `setInterval`。
- 日志只用 `ctx.logger`，不用 `console.log`。
- 面向用户文案走 `ctx.locale` 或客户端 `locale` 服务，不硬编码中文进渲染函数。

## 4. 客户端半规范

### 4.1 形态：手写 `__ModuleLoader__` bundle

**【已核实】** 浏览器半**不是 ESM**，不能 `import`。它必须在加载时调用全局 loader：

```js
window.__ModuleLoader__.load({
  id: 'dsh-peerbar',                       // 必须等于包名
  factory: (require) => {
    const module = { exports: {} }
    const exports = module.exports
    const React = require('react')
    const { MenuItemButton } = require('@deepseek-ai/dsh-client-ui-primitives')
    // ... 组件 ...
    exports.apply = apply
    exports.inject = ['slots', 'locale']
    return module.exports
  },
})
```

- `id` 必须与 package name 一致（entry id == 包名）。
- 可 `require` 的：`react`、`react/jsx-runtime`、`react-dom`、`@deepseek-ai/dsh-client-ui-primitives`，以及你在 `dsh.client.inject` 里声明的包。
- 不写 `import`/`export` 语句；`name/apply/inject` 挂在 `module.exports` 上。
- 官方文档给了 TypeScript 版的 `import` 写法，那是**源码形态**（构建后仍是 loader bundle）。本项目「零构建」= 直接写这个 wrapper。可参考 `~/.dsh/profiles/desktop/node_modules/@ychris12138/dsh-usage-stats/lib/client.js`（2165 行，纯手写，无构建，且就装在桌面版里跑）。

### 4.2 slot 注册：唯一合法的 UI 扩展方式

```js
ctx.effect(() => ctx.locale.register('dsh-peerbar', { zh, en }), 'peerbar: dicts')
ctx.slots.inject('settings.section', () => ctx.slots.register({
  name: 'settings.section',
  id: 'peers',
  order: 900,
  label: () => t('section.peers'),   // thunk 会随语言重读
  locale: 'dsh-peerbar',
  inject: () => ({ ...callbacks }),
}, PeersSection))
```

**【已核实】** 规则（`docs/subsystems/slots.zh.md` + slot 目录）：

| 概念 | 规则 |
| --- | --- |
| 必须 `ctx.slots.inject(key, cb)` | 即使 owner 已经在场也要用；它在声明生命周期内注册，owner 折叠时自动移除，恢复时重注册 |
| 注册即认领 | 不能向**未声明**的 slot 注册；不能重复声明别人已拥有的 child；违反在加载期抛错 |
| `single` | 只有一个 cell，渲染**优先级胜者**；想并列内容应自己声明 child slot，而不是当列表用 |
| `list` | 必须有唯一 `id`，按 `order` 再按注册顺序排；复用官方 id = 遮蔽那一项 |
| `keyed` | owner 传 `entryKey`；注册已占用的 key = 替换该占用者 |
| `chain` | 每项给纯 `select(owner)`，按优先级选第一个非 null |
| `scope` | `root` / `session-maybe` / `session`；`session` 会强制建立 Session 绑定 |
| 组件拿不到 `ctx` | 数据只能经：owner props、注册项的 `inject` factory、slot store、`locale` 的 `t`、标准 props 里的 hooks |
| 标准 hooks（全 scope 可用） | `useWorkspaces`、`useSessions`、`useSessionStatus`、`useSessionAccess`、`useWorkspaceAccess`、`usePanelInfo`、`useRemoteAccess` |
| 跨包只能 `import type` | 运行时禁止 import 别的功能包的实现 |

**【已核实】** 摘自 slot 目录（`replaceRisk` 是官方标注的替换风险）：

| slot | 基数/作用域 | 现有占用 | 用途 | replaceRisk |

## 5. 对《需求交接》假设的核对结论

| # | 需求文档的说法 | 核实结论 | 影响 |
| --- | --- | --- | --- |
| 1 | §8.2 / §11-1：注入 `sidebar.workspaces` 加过滤条、把远端行铺进同一棵树 | **不成立**。该 slot 是 `single`，由 ui-sidebar 声明、ui-workspace 独占；官方标注 `shadows-shipped-ui`。`registerOptions` 为空，没有「追加一行」的口子 | **P0-2/P0-3 必须改设计**，见 §6 |
| 2 | §8.2：会话行操作挂 `sidebar.workspaces.session.row.action`、右键菜单挂 `.session.menu.item` | **成立**，两个都是 root 作用域 list，`inject` 里给 `hooks.menuOpenState` | 可用于「在远端打开」「复制远端 ID」 |
| 3 | §11-2：`settings.section` 存在 | **成立**，list/root，`registerOptions: id/order/label`，owner props 有 `close()` | P0-1 直接可用 |
| 4 | §11-3：`webServer.register({kind, path, handler})` / `registerUpgrade` / `.port` / `.protocol` / `.getOrigin()` | **全部成立**；补充：handler 是原生 `(req,res)`，且**路由无认证**（§3.3） | P0-5 要自己写 guard |
| 5 | §8.3：用 `ctx.inject(['webServer'], ...)` 等就绪 | 建议改成静态 `export const inject = ['webServer']` | 规避 fleet 踩过的坑 |
| 6 | §9：远端白名单里写 `GET /api/session/list` | **形态错**。Remote 调用是 `POST /api/<namespace>/<method>`，body `{ args: {...} }`；流式方法走 WS `/api/remote.mux`。且整条 `/api` 受浏览器 cookie + Host/Origin 信任保护 | S1 的探测要按 POST + 信封来验 |
| 7 | §11-5：`dsh.bundle.patch` + `dsh.client.inject` + peer 依赖 cordis | **成立**；补充 `exports["./client"]`、`platform: 'web'`、`engines.dsh` 三个必需项 | 清单照 §2.1 写 |
| 8 | §11-6：0.2.1-rc.2 内核没有远程 Host 能力 | **成立但需精确化**：有 `dsh-api-remotes` / `dsh-api-remote-access`，但它们是**同进程** Host↔Client 的 Typert 转发与访问控制，不是「跨机器 dsh」。跨机能力确实要插件补 | 定位不变 |
| 9 | §8.1：跨机请求全由宿主半发起 | **成立且必要**。浏览器跨 origin 拿不到远端 cookie（host-only + SameSite=Strict）；宿主半持有 cookie 才是唯一可行路径 | 架构结论保留 |
| 10 | §13：零第三方依赖、手写 ESM、`dsh.client` 直指 `client/client.js` | **成立**；但客户端文件必须是 loader bundle（§4.1），不能是 ESM 模块。`usage-stats` 就是这么干的 | 目录结构可行，文件名建议 `lib/client.js` 与 `lib/index.js` 对齐 `exports` |

## 6. 侧栏聚合：可行方案对比（**必须先定**）

`sidebar.workspaces` 被 ui-workspace 独占，官方只给两条路：

### 方案 A（推荐 v0.1）：独立面板 + 中栏整页

- 侧栏：`sidebar.panellist` 加一个 `id: 'peerbar'` 的图标（追加，零风险）。
- 中栏：`main` 加 `key: 'peerbar'` 的整页（与 plugin-manager / schedule 同款），页面里自绘「全部 Host → 工作区 → 会话」平铺树、过滤条、搜索。
- 宿主：`/dsh-peerbar/api/state` 供数据。
- 代价：不是「原生侧栏里混排」，而是「侧栏多一个入口，点开是聚合视图」。
- 好处：完全不碰官方 UI，升级不炸，验收项 §15 里「关闭插件后侧栏完全恢复原生形态」天然满足。

### 方案 B：遮蔽 `sidebar.workspaces` 整块重绘

- 官方允许（single 渲染优先级胜者），但 `replaceRisk: shadows-shipped-ui`。
- 你必须自己重画：section header、搜索框、分组/平铺切换、拖拽排序、置顶/归档过滤、重命名/Fork/归档对话框（这些现在都在 ui-workspace 内部）。
- 能拿到的只有 `SidebarSectionOwnerProps{wide, expandSidebar}` 和标准 hooks（`useWorkspaces`/`useSessions`）——**拿不到** ui-workspace 的私有视图状态。
- 结论：工作量 ≈ 重写 ui-workspace，且每次 dsh 升级都要跟。**不建议 v0.1 做。**

### 方案 C：只加行级 action

- 在 `session.menu.item` 加「在远端打开」「复制远端会话 ID」。
- 做不到「一眼看清哪台机器」。

## 7. 跨机访问：0.2.1-rc.2 的鉴权现实

**【已核实】**（`dsh-client-connection/README.zh.md` §浏览器认证与请求信任）：

1. 每个进程生成一个**随机启动令牌**，`dsh web` 打印并打开 `?token=...` 的 URL。
2. `GET /` 接受该令牌 → 写入**绑定 authority 的签名 cookie** → 303 到干净的 `./`。cookie 是 host-only / `Path=/` / `HttpOnly` / `SameSite=Strict`，HTTPS 监听时带 `Secure`，**cookie 名与签名 audience 含 scheme**（http 的 cookie 拿去打 https 无效）。有效期 `cookieMaxAgeDays` 默认 30 天。
3. 签名密钥存在 `ctx.credentials` 的 `client-connection/browser-session` grant 里，本地落 `$DSH_HOME/.credentials.yaml` → **cookie 能跨进程重启存活**，但**换取它用的启动令牌每次启动都变**。
4. 另有 API 通道：`GET /connect?token=...&interactions=none` → 302 + 签名 API cookie（owner principal）。HTTP 可先于 WS 建立。这是**给非浏览器客户端**设计的入口。
5. `/api` 上先做 Host/Origin 信任（403），再做认证（401）；`dsh web --host 0.0.0.0` 不支持，非回环绑定要用 `--trusted-host`。

对本项目的直接含义：

- S1 有两条候选路线，都比「模拟浏览器」干净：**(a) 让用户粘贴一次远端启动令牌，宿主半走 `GET /connect?token=…&interactions=none` 换 API cookie 并自管 jar**；**(b) 远端也装 peerbar，暴露一个只读的 `/dsh-peerbar/api/state`（远端自己是 owner，本地直接读自己的 service）**。**(b) 更稳**——不碰 dsh 内部鉴权，也顺便解决 S3 的「会话正文谁给」。
- 社区先例支持 (b)：`dsh-fleet` 就是让远端跑一个带 `?token=` 的自有网关端口（33180），完全不依赖 dsh 的 cookie。
- S2（自签证书）与需求 §12 判断一致：Node 侧 `fetch` 会对 `192.168.3.50` 自签证书报 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`；per-host `insecure` 开关或 `NODE_EXTRA_CA_CERTS` 都可，后者更安全。
- 若坚持走 (a)，注意 **`/api` 不是 REST**（§5-6）：会话列表是 `POST /api/session/list`（`{args}` 信封），流式投影要 WS `/api/remote.mux` + Typert 编解码。宿主半要自己实现这套协议的成本**只对「要一直跟流」的场景才高**；只读一帧的话见 §7.1，一个帧编解码 + 一条 open 消息就够（`lib/stream.js` 实测约 200 行）。

### 7.1 远端归档集与只读流（2026-10-23 实测）

**【已核实】** 三条硬事实，都踩过：

1. **`session/list` 不返回归档状态**。item 上只有 `sessionId` / `updatedAt` / `running` / `blank` / `cwd` / `origin` / `parentSessionId` / `projections`（`dsh-api-session-controller/lib/index.js:1940-1952` 的 `summaryFor` 与 `:2127` 的 `listFields`）。归档集存在 workspace registry（`~/.dsh/storages/workspace.json` 的 `global.archivedSessionIds`），对外**只有 `workspace/follow` 这条流**给（`dsh-api-workspace-controller/lib/index.js:963` 的 `follow`，首帧 `{type:'baseline', value:{items, archivedSessionIds, pinnedSessionIds}}`）。没有 `workspace/list` 之类的一元端点（`dsh-api-workspace-controller/lib/typert.host.js` 的方法清单里只有 create/delete/rename/insertBefore/insertSessionBefore/archiveSession/unarchiveSession/pinSession/unpinSession/follow）。
2. **流只能走 WS**。`POST /api/workspace/follow` 会被网关拒：`gateway/signature-invalid` "stream Remote methods must be opened through the stream carrier"（`dsh-api-gateway/lib/index.js:980` 的 `openWireStream`）。WS 路径固定 `/api/remote.mux`，帧是纯 JSON：
   - 客户端 → 宿主：`{type:'open', streamId, endpoint, payload:{args}}`、`{type:'cancel'|'end', streamId}`
   - 宿主 → 客户端：`{type:'item', streamId, value}`、`{type:'end', streamId}`、`{type:'error', streamId, error:{code,message,details}}`
   （`dsh-api-gateway/lib/index.js:236-251`；宿主每 2s 发一次 Ping，客户端要回 Pong，`DEFAULT_WEBSOCKET_HEARTBEAT_INTERVAL_MS`。我们读完首帧就关，来不及触发心跳。）
3. **拿探活 cookie 去升级 WS = 探活 cookie 当场作废**。`admitConnection` 会把升级的 socket 记成 peer 的所有者，socket 一关就 `peers.delete(peer.id)`（`dsh-client-connection/lib/index.js:759-775`）；cookie 里签的就是那个 peer id，下一个 RPC 直接 401。实测：换 cookie → `list` 成功 → 升级 WS 读 baseline → 关 socket → 再 `list` 必 401。
   **对策**：给流**现换一张专用 cookie**（`exchangeCookie`），读完随 socket 关闭一起消亡；探活继续用自己那张。这样既不互相污染，也不会在远端攒 peer（专用 peer 由 socket 关闭时回收）。

`origin === 'subagent'` 的子代理会话**永远不进侧栏**：官方 `sessionVisible` 第一句就是 `if (session.origin === "subagent") return false`（`dsh-client-ui-workspace/lib/client.js:964-974`）。`session/list` 会把这些子会话一起返回，不自己过滤就会铺成一堆重复行。

## 8. 本地开发流程（本机实测）

**【已核实 2026-10-22】** 现状：

- `pacman -Qs` 只有 `dsh-desktop-linux-bin 0.2.1rc.2-1`；**`dsh` 不在 PATH**，`/usr/sbin/dsh`、`/usr/bin/dsh` 都不存在；`~/dsh-web.sh` 也已不存在。日常宿主是 **DSH Desktop**，profile 为 `~/.dsh/profiles/desktop`。
- 桌面包里**带着完整 CLI**：`.../app/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js`（`--version` → `0.2.1-rc.2`），但 `desktop` profile 被 Electron 独占，**任何命令（含 `--dump-config`）都被拒绝**，只能走桌面版 UI。
- 桌面包**自带运行时**：`/opt/dsh-desktop-linux-bin/resources/runtime`，`bin/node` 是 Electron 的 Node 包装器（需 `DSH_DESKTOP_NODE_EXECUTABLE=/opt/dsh-desktop-linux-bin/deepseek-harness`），实测 Node 24.21.0 / pnpm 11.28.5。系统本身**没有 pnpm**。
- 桌面版的页面载体是 `http://127.0.0.1:<随机端口>/?token=…`（`dsh-desktop-host` 里 `ctx.webServer` 真实监听，`connection.authenticatedUrl()` 只加启动令牌，Electron 再加载该 URL）→ **插件注册的 `/dsh-peerbar/api/*` 与页面同源，行为与 `dsh web` 一致**；但端口每次随机，不能写死 3080。

装插件（唯一路径）：

```
侧栏「插件」→ 标题旁箭头 → 安装第三方插件 → /home/nwj/Projects/dsh-peerbar
```

改代码生效方式：客户端半重载窗口（profile 启用了 HMR）；宿主半**重启 DSH Desktop**。

需要 CLI 时另起独立 profile，不要碰 desktop：

```sh
RT=/opt/dsh-desktop-linux-bin/resources/runtime
export DSH_DESKTOP_NODE_EXECUTABLE=/opt/dsh-desktop-linux-bin/deepseek-harness
DSH="$RT/bin/node /opt/dsh-desktop-linux-bin/resources/app/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js"

$DSH --profile web --dump-config | grep -A4 '# == dsh-peerbar'   # 只读，可用
sudo pacman -S pnpm                                              # dsh plugin 转发给 PATH 上的 pnpm
alias dsh="$DSH"
dsh plugin --profile web add link:/home/nwj/Projects/dsh-peerbar
dsh web --no-open
```

**当前 profile 的 bundles 顺序**（`web` 与 `desktop` 内容相同，`patchReload: live`）：
`@deepseek-ai/dsh-base` → `@deepseek-ai/dsh-web-app` → `dshmarket` → `@ychris12138/dsh-usage-stats`。
peerbar 会追加在最后，能覆盖前面各层的行（覆盖时要**重述该行所有键**，patch 不是深合并）。

排障要点：

- 客户端 slot 注册失败 → 整块 UI 不出现、页面 console 报错；宿主路由失败 → 日志里 `[peerbar]` 行。
- `--dump-config` 里看不到你的层 = patch 没被应用（检查 `dsh.profile.bundles` 与包名拼写）；desktop profile 只能看桌面版插件页的清单。
- `web` 与 `desktop` 是两套 profile，各装各的——在 `web` 上验证通过不代表桌面版已生效。
