## 2. T2 调研结论（开工前已确认，避免走弯路）

**渲染路径（可行，且改动很小）**：

官方的图片缓存 `HistoricalImageCache.loadCanonical` 调的是
`binding.session.readAttachment(attachmentId)`，拿到
`{ok:true, value:{attachment:{mediaType,...}, data:number[]}}` 后自己转 Blob URL。
我们合成的远端 binding **已经有 `readAttachment` 这个方法**，一期里它返回
`peerbar/unsupported` —— 也就是说**只需要实现它，官方缓存自动就能用**，
不用 patch `imageUrl`。

远端端点：`session/attachment {request:{sessionId, attachmentId}}`
→ `{attachment:{attachmentId, mediaType, bytes, width, height, name?}, data: <base64>}`。
注意 `data` 是 **base64 字符串**，而 readAttachment 契约要 **number[]**，
中间要做一次 decode。

**发送路径（待验证）**：`fileUploads/upload` 有两个参数——`agent`（lookup，
wire 名 `agentId`，值是 sessionId）+ `request {data: base64, name?}`，
返回 `{receiptId, file:{attachmentId, name, bytes}}`。lookup 参数能否通过
我们的 RPC 信封传，需要实测；不行就降级为 composer 禁用附件 + 提示。

### T17 为什么不做：关键调研结论（省下以后重走）

远端 `workspaceFiles/*` 端点本身**没问题**（脚本实测）：

```
workspaceFiles/list  {workspaceFileScopeId:<sessionId>, path}  → {entries:[{name,type,size}], truncated}
workspaceFiles/read  {workspaceFileScopeId, path, range:{}}    → {absolutePath, version, bytes, offset, text, lines, eof}
workspaceFiles/stat  {workspaceFileScopeId, path}              → {absolutePath, version, bytes}
```

`range` 是严格必填（内容可为 `{}`），这是个容易踩的点。

但**客户端 hook 点不对**：官方 `sidebar-files` 用的是 `ctx.remote.workspaceFiles`，
而 `ctx.remote` 实测是「连接级 face」——`Object.keys(remote)` =
`ctx,name,ownerCtx,connection,namespaces,hostFacts,streams,events,mutations`，
`namespaces` 是个 `Map`，当前只有 `productAnalytics,remoteAccess,agentPresets,commands,credentials,settings`，
**没有 `workspaceFiles`**。它由 `dsh-api-workspace-files` 的 provider 在别的时机装配，
我们拿不到可替换的实现对象（proto 上的 `invokeMethod`/`installNamespace` 可能是正确入口，
但那是更深的内部机制，风险高于收益）。

要继续，路线是：
1. patch `remote.invokeMethod` / `installNamespace`（低层，需更多实测）；或
2. 等官方提供「跨 host 文件抽象」；或
3. 自己做一个「远端文件」面板（独立 UI，不接管官方面板）
