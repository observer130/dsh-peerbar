## 2. T2 调研结论（开工前已确认，避免走弯路）

**渲染路径（可行，且改动很小）**：

官方的图片缓存 `HistoricalImageCache.loadCanonical` 调的是
`binding.session.readAttachment(attachmentId)`，拿到
`{ok:true, value:{attachment:{mediaType,...}, data:number[]}}` 后自己转 Blob URL。
我们合成的远端 binding **已经有 `readAttachment` 这个方法**，一期里它返回
`peerbar/unsupported` —— 也就是说**只需要实现它，官方缓存自动就能用**，
不用 patch `imageUrl`。

远端端点：`session/attachment {request:{sessionId, attachmentId}}`
→ `{attachment:{attachmentId, mediaType, bytes, width, height, name?}, data: <base64>}`。
注意 `data` 是 **base64 字符串**，而 readAttachment 契约要 **number[]**，
中间要做一次 decode。

**发送路径（待验证）**：`fileUploads/upload` 有两个参数——`agent`（lookup，
wire 名 `agentId`，值是 sessionId）+ `request {data: base64, name?}`，
返回 `{receiptId, file:{attachmentId, name, bytes}}`。lookup 参数能否通过
我们的 RPC 信封传，需要实测；不行就降级为 composer 禁用附件 + 提示。

### T17 为什么不做：关键调研结论（省下以后重走）

远端 `workspaceFiles/*` 端点本身**没问题**（脚本实测）：

```
workspaceFiles/list  {workspaceFileScopeId:<sessionId>, path}  → {entries:[{name,type,size}], truncated}
workspaceFiles/read  {workspaceFileScopeId, path, range:{}}    → {absolutePath, version, bytes, offset, text, lines, eof}
workspaceFiles/stat  {workspaceFileScopeId, path}              → {absolutePath, version, bytes}
```

`range` 是严格必填（内容可为 `{}`），这是个容易踩的点。

但**客户端 hook 点不对**：官方 `sidebar-files` 用的是 `ctx.remote.workspaceFiles`，
而 `ctx.remote` 实测是「连接级 face」——`Object.keys(remote)` =
`ctx,name,ownerCtx,connection,namespaces,hostFacts,streams,events,mutations`，
`namespaces` 是个 `Map`，当前只有 `productAnalytics,remoteAccess,agentPresets,commands,credentials,settings`，
**没有 `workspaceFiles`**。它由 `dsh-api-workspace-files` 的 provider 在别的时机装配，
我们拿不到可替换的实现对象（proto 上的 `invokeMethod`/`installNamespace` 可能是正确入口，
但那是更深的内部机制，风险高于收益）。

要继续，路线是：
1. patch `remote.invokeMethod` / `installNamespace`（低层，需更多实测）；或
2. 等官方提供「跨 host 文件抽象」；或
3. 自己做一个「远端文件」面板（独立 UI，不接管官方面板）

### 顺手确认的

## 7. 三期补充：T4 + T17（2026-10-26）

二期留下的两个「点了没反应」在三期修掉了，用的是**同一个拦截点**。

### 根因（两项同源）

命令面板与文件面板都走 `ctx.remote.{commands,workspaceFiles}.*`，而 `ctx.remote`
是**连接级 face**（绑定本机 host）——远端 sessionId 被传进本机 gateway 必然失败。

### 为什么 patch `invokeRemote` 而不是逐个 patch 方法

`RemoteNamespaceService` 的方法（`list`/`execute`/`read`…）是 getter
（`Object.defineProperty`），每次访问都返回新闭包，直接覆盖 `service.list`
会被下次 getter 求值打回原形。`invokeRemote` 是**实例属性**（构造器里
`this.invokeRemote = invokeRemote`），一换就全拦住，而且 `direct.descriptor`
里带 `namespace/method`，能精确路由到对应 RPC 端点。

## 8. 三期验收反馈（第三轮修复，2026-10-27）

用户复核结果：模型切换、压缩已通过；「@」仍闪退、文件面板一直「正在读取…」。
两项都是上一轮补丁的**残留缺口**，不是新问题。

| 反馈 | 根因 | 修法 |
| --- | --- | --- |
| 「@」弹窗一闪而过 | 候选来自 `ctx.remote.{fileReferences,sessionReferenceResolver,skills}`，只拦了 commands/workspaceFiles/session → 远端 sessionId 进本机 gateway → 候选 promise reject → input-trigger `source-failed` → 菜单关闭 | 三个 namespace 加进 `invokeRemote` 拦截；端点进白名单；wire 形状实测 `fileReferences/list {agentId,query}`、`sessionReferenceResolver/candidates {agentId,query}`、`skills/list {request:{sessionId}}` |
| 文件面板卡「正在读取…」 | 官方 `DirectoryNode.open()` 的初始列表由 watch 流**第一条 `ready` 事件**触发；上一版把流做成「永不 yield 的挂起流」，首屏 list 永不发 | 先 yield `{kind:'ready'}` 触发首次 list，之后挂起（订阅已建立、暂无变更）；`dispose()` 唤醒挂起迭代并返回 done |
| 页面报错 `slot "sidebar.workspaces.directoryFlow" is already declared` | 官方 entry 被影子替换后，其 `children` 声明**仍然生效**；我们重复声明同一批 key 冲突 | `register` 不再声明子座位（实测 `spec()` 对 directoryFlow / session.menu.item / row.leading 均存在，directory-picker 注入目标仍在、「添加工作区」正常） |

### 实测（headless Chrome + nv50，rc.3）

- 「@」：候选 **70 项**文件/目录，1.2s / 3.0s / 4.8s 三次采样均在（修复前 <1s 消失）；console 无 `skills/list failed`
- 文件面板：列出 `/home/nwj/data` 的目录与文件，正文无「正在读取」「读取失败」「Directory watch ended」
- 服务端直测：`fileReferences/list` 20 项、`sessionReferenceResolver/candidates` 50 项、`skills/list` 正常
- 58 单测 + ui-check **全部断言通过**（`consoleErrors` 空）

### 结论（写给以后的自己）

- **流式 stub 的关键不是「别结束」，而是「先给一条 readiness」**：官方目录树的
  首屏完全依赖 `ready` 事件；给完再挂起，既不发假变更，也不会报 watch ended。
- **namespace 拦截要按「UI 入口」清点**，不能按「我想到的功能」清点：`@` 用三个
  namespace、模型用一个，漏任何一个都表现为「入口点了没反应」。
- **影子替换只替换渲染，不替换声明**：children 由官方 entry 声明即可，重复声明
  是硬报错（不是 warning）。

### 补充：「+」菜单的「文件」在远端会话里改为浏览远端（2026-10-27）

官方 `file` 命令（📎）的 run 是 `inputHub.pickFiles()` → **原生文件对话框**，语义是
「上传本地附件」（选完由 `fileUpload.upload` patch 传到远端），本机会话也一样。
远端会话里用户期待的是「浏览远端目录」，所以按归属分流：

| 场景 | 「文件」（现已改名） | 「上传本地文件」 |
| --- | --- | --- |
| 远端会话 | 改名「远端文件」→ 往输入框插 `@`，复用官方引用菜单列远端候选 | 保留（原 `pickFiles`） |
| 本机会话 | 原样（原生对话框） | 不出现 |

接管点两个（都必要）：
1. `commandUi.register` 包一层（**实例属性覆盖原型方法**——和 namespace 的 getter
   坑同源，原型方法可以这样改；getter 不行）
2. `commandUi.live.contributions.get('file')` 直接替换（官方比我们先注册时走这条）

冒烟注意：新贡献的 `icon` 必须是**组件类型**，`prim()` 返回的是元素——传错会让整个
指令菜单抛 `React #130`，表现是 `/` 和 `+` 都弹不出菜单，极容易被误判成拦截失效。
